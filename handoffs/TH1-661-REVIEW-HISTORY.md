Findings, ordered by severity (all are static control-flow findings, not executed reproductions):

1. **P1 — ACP can wait forever before TERM/KILL starts (claim 2; also stalls a racing prompt).** `packages/server/src/server/agent/providers/acp-agent.ts:2443` awaits `connection.unstable_closeSession` without a deadline when the provider advertises close support; the 2s TERM + 2s KILL phase only starts at `:2463`. A provider that accepts the request but never replies and stays alive never reaches escalation. The installed ACP SDK 0.17.1 implements this as an unresolved response promise with no timer (`node_modules/@agentclientprotocol/sdk/dist/acp.js:894–900`; method forwarding at `:546–547`). `agent-manager.ts:2106` awaits that close with no outer deadline, and `:1423` keeps the loader behind its lifecycle tail, so cleanup retry cannot even begin. This path is distinct from the bounded failure/rejection covered in the existing test. The repo already uses a deadline for the same RPC in ACP probe cleanup (`acp-agent.ts:1457–1466`). Fix: make graceful provider RPC shutdown time-bounded, then proceed with owned-process escalation even when the RPC never settles; retain ownership until confirmed exit. OpenCode also awaits `session.abort` without a close deadline (`opencode-agent.ts:547`, `:5058`) before reaching server release at `:5069`; its ordinary interrupt path already has a 2s cap (`:3633`). The ACP path alone establishes this finding.

2. **P1 — Reload bypasses the new pending-cleanup barrier (claim 2).** After `session.close()` succeeds but the manager's descendant reaper fails (`agent-manager.ts:2106–2114`), the old session remains registered and `idleReapPending`/`idleProcessSnapshots` remain set. The ordinary loader retries cleanup at `:1425–1429`, but the user-facing Reload handler sees that registered session and calls `reloadAgentSession` directly (`session.ts:4605–4610`). That path calls only `closeReloadedSession(existing.session)` (`agent-manager.ts:1892`, `:1977`), publishes closure at `:1895`, and resumes a replacement at `:1901`; it never invokes the retained tree reaper or clears its flags. `prepareAgentForClosure` at `:4568–4603` and registration at `:4341` do not clear them either. Thus a fresh runtime can be admitted while the captured old descendants still survive; the next ordinary access can close the replacement using the stale pending-cleanup state. Fix: every replacement path must complete the retained cleanup before publishing/resuming and clear state against the runtime it belongs to. Serialization alone does not enforce that invariant.

3. **P1 — One stalled idle close blocks every later agent and all future sweeps (claim 3).** `packages/server/src/server/agent/agent-manager.ts:1376` iterates all resident agents sequentially and `:1405` awaits each close before visiting the next. Put the unresponsive ACP session from finding 1 before an idle Codex/Claude/Pi session: the later close is never attempted. `bootstrap.ts:604` rejects overlapping sweeps and `:610–611` only resets its flag when the hung sweep settles, so later timers cannot make progress either. Fix: independent bounded per-agent closure attempts, preserving each agent's lifecycle lane and process ownership. The reported OpenCode fix at `providers/opencode/server-manager.ts:505–518` does correctly continue after a rejected `killServer` and retain failed generations; provider-wide daemon shutdown also invokes clients independently with per-client catches (`provider-registry.ts:946–955`), and daemon agent shutdown is concurrent with a 5s per-agent cap (`bootstrap.ts:1955–1969`). Those corrected paths do not protect the feature's idle sweep.
